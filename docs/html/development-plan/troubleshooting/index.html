개발 계획서로 돌아가기

개발 단계 트러블슈팅

해결 완료 10단계 Next.js 백엔드, Supabase, Vercel 확장 과정에서 실제로 발생한 오류를 시간 순서로 정리한다. 각 항목은 초보자가 같은 문제를 다시 만났을 때 원인, 이유, 해결책을 따라 확인할 수 있도록 작성한다.

1. 타임라인 요약

순서 증상 핵심 해결
T1 Vercel 빌드 후 No Output Directory named "public" 오류가 발생했다. Vercel 프로젝트 기준을 server/next-app로 잡고 Output Directory를 비웠다.
T2 배포 URL에서 /gallery 직접 접속 시 404가 발생했다. Next.js rewrites로 SPA 경로를 /index.html에 연결했다.
T3 Preview URL이 바뀔 때마다 CORS 오류가 발생했다. 운영 클라이언트는 같은 origin의 /api를 호출하게 하고, 서버 CORS는 Vercel preview 패턴을 허용했다.
T4 /api/health가 동작하지 않고 404를 반환했다. 정적 사이트가 아니라 Next.js 앱으로 배포되도록 Root Directory, Framework, Output Directory 설정을 정리했다.
T5 Vercel 빌드에서 JSX 타입 오류가 대량으로 발생했다. 서버 빌드 스크립트가 클라이언트 devDependencies까지 설치한 뒤 Vite 빌드를 수행하게 수정했다.
T6 GET /api/drawings가 permission denied for table drawing_projects로 실패했다. Supabase 테이블에 필요한 PostgreSQL GRANT 권한을 추가했다.
T7 POST /api/drawings가 외래 키 제약 조건 위반으로 실패했다. Supabase Auth에 실제 서비스 사용자를 만들고 그 User UID를 APP_SERVICE_USER_ID로 사용했다.

2. 상세 기록

T1

Vercel Output Directory 오류

해결 완료

Vercel 빌드가 끝난 뒤 No Output Directory named "public" found after the Build completed 오류가 발생했다.

1. 원인 Vercel 프로젝트가 Next.js 앱이 아니라 정적 산출물 배포처럼 설정되어 있었고, Output Directory가 public로 지정되어 있었다.
2. 이유 저장소가 client/와 server/next-app/로 나뉜 구조라 Vercel이 어느 폴더를 앱 루트로 봐야 하는지 명확해야 한다. Next.js 배포에서는 public을 최종 Output Directory로 지정하지 않는다.
3. 해결책 Vercel 프로젝트 설정에서 Root Directory를 server/next-app, Framework Preset을 Next.js, Build Command를 npm run build, Output Directory를 빈 값으로 설정했다. 
Root Directory: server/next-app
Framework Preset: Next.js
Build Command: npm run build
Output Directory: 비워둠
T2

/gallery 직접 접속 404

해결 완료

처음 접속 화면을 갤러리로 바꾸고 클라이언트 라우팅을 추가한 뒤, 배포 URL의 /gallery에 직접 접속하면 404가 발생했다.

1. 원인 /gallery와 /canvas는 React 클라이언트 라우트인데, 브라우저에서 직접 주소를 열면 요청이 먼저 Next.js 서버와 Vercel 라우팅으로 들어갔다.
2. 이유 SPA 라우팅은 index.html이 로드된 뒤 브라우저에서 해석된다. 서버가 해당 경로를 정적 파일 또는 Next.js 페이지로 찾으면 실제 파일이 없어서 404가 된다.
3. 해결책 server/next-app/next.config.mjs에 rewrites를 추가해 /gallery, /canvas 요청을 /index.html로 넘겼다. 
{
  source: '/gallery',
  destination: '/index.html'
},
{
  source: '/canvas',
  destination: '/index.html'
}
T3

Vercel Preview URL 변경과 CORS 오류

해결 완료

배포가 반복되면서 web-drawing-... 형태의 Preview 주소가 계속 바뀌었고, 클라이언트가 다른 Preview 주소의 API를 호출하면서 CORS 오류가 발생했다.

1. 원인 Production/Preview 환경의 VITE_API_BASE_URL이 특정 배포 URL로 고정되어 있었다. 그래서 현재 페이지 origin과 API origin이 서로 달라졌다.
2. 이유 Vercel은 배포마다 고유 Preview URL을 만든다. 이전 Preview URL을 API 주소로 유지하면 새 Preview 페이지에서 이전 Preview API를 호출하게 되고, 서버가 현재 origin을 허용하지 않으면 브라우저가 요청을 차단한다.
3. 해결책 운영 빌드에서는 클라이언트가 항상 같은 사이트의 /api를 호출하게 바꿨다. 서버 middleware에는 대표 도메인과 Vercel Preview 도메인 패턴을 CORS 허용 목록으로 추가했다. 
// production/preview
fetch('/api/drawings')

// local development
VITE_API_BASE_URL=http://localhost:5174

운영 Vercel 환경 변수에는 VITE_API_BASE_URL을 넣지 않는 것이 안전하다. 넣어야 한다면 같은 배포의 origin을 가리키는지 매번 확인해야 한다.

T4

/api/health 404

해결 완료

/api/health가 계속 404를 반환했다. 이 문제는 API 코드 자체보다 Vercel 배포 설정 문제에 가까웠다.

1. 원인 Vercel이 server/next-app의 Next.js API Routes를 배포하지 않고, 정적 산출물만 배포하는 흐름으로 동작했다.
2. 이유 /api/health는 Next.js 서버 라우트다. Next.js 프로젝트로 배포되지 않으면 Vercel에 해당 함수가 생성되지 않으므로 플랫폼 수준의 404가 발생한다.
3. 해결책 Vercel Root Directory를 server/next-app로 확정하고, Output Directory를 비운 뒤 재배포했다. 이후 /api/health가 응답하는지 먼저 확인한 다음 갤러리 API를 확인하는 순서로 점검했다.
T5

Vercel 빌드 중 JSX 타입 오류

해결 완료

Vercel 빌드에서 JSX element implicitly has type 'any' because no interface 'JSX.IntrinsicElements' exists 오류가 여러 컴포넌트에서 발생했다.

1. 원인 Vercel 빌드 중 client/ 의존성을 설치할 때 React 타입 패키지 같은 devDependencies가 빠졌다.
2. 이유 서버 앱 기준으로 빌드하면서 내부에서 클라이언트 빌드도 수행한다. 이때 production 환경으로 npm ci가 실행되면 TypeScript 빌드에 필요한 @types/react 계열 devDependencies가 설치되지 않는다.
3. 해결책 server/next-app/scripts/build-with-client.mjs에서 클라이언트 의존성을 npm ci --include=dev로 설치하게 했다. 클라이언트 빌드 후 client/dist를 server/next-app/public으로 복사하고 Next.js 빌드를 실행한다. 
npm ci --include=dev
npm run build
copy client/dist -> server/next-app/public
npm run build:next
T6

Supabase 테이블 권한 오류

해결 완료

GET /api/drawings 호출이 500으로 실패했고, Vercel 로그에는 permission denied for table drawing_projects가 출력되었다.

1. 원인 Supabase의 drawing_projects 테이블에 API에서 사용하는 역할의 PostgreSQL 권한이 부여되어 있지 않았다.
2. 이유 RLS 정책은 행 단위 접근 조건을 정하는 기능이고, 테이블 자체에 접근할 수 있는 권한을 자동으로 부여하지 않는다. 즉, RLS가 있어도 grant select, grant insert 같은 테이블 권한이 없으면 쿼리가 실패한다.
3. 해결책 Supabase SQL Editor에서 public schema와 관련 테이블에 필요한 권한을 부여했다. 이후 목록 조회 API가 DB에서 작업 목록을 읽을 수 있게 되었다. 
grant usage on schema public to anon, authenticated, service_role;

grant select, insert, update, delete on public.profiles to authenticated, service_role;
grant select, insert, update, delete on public.drawing_projects to authenticated, service_role;
grant select, insert, update, delete on public.uploaded_images to authenticated, service_role;
grant select, insert, update, delete on public.share_links to authenticated, service_role;
T7

저장 시 사용자 외래 키 제약 조건 위반

해결 완료

POST /api/drawings 호출이 500으로 실패했고, 로그에는 drawing_projects_user_id_fkey 외래 키 제약 조건 위반이 출력되었다.

1. 원인 서버가 사용하는 APP_SERVICE_USER_ID 값이 auth.users 테이블에 실제로 존재하지 않는 UUID였다.
2. 이유 drawing_projects.user_id는 Supabase Auth의 사용자 ID를 참조한다. public.profiles에 같은 UUID를 넣는 것만으로는 충분하지 않고, 먼저 auth.users에 실제 사용자가 있어야 한다.
3. 해결책 Supabase Dashboard의 Authentication 메뉴에서 개발용 사용자를 생성하고, 생성된 실제 User UID를 Vercel의 APP_SERVICE_USER_ID 환경 변수로 등록했다. 필요하면 같은 UID로 public.profiles row를 추가한다. 
insert into public.profiles (id, email, display_name)
values (
  'Supabase Auth에서 복사한 실제 User UID',
  'developer@webdrawing.local',
  'Developer'
)
on conflict (id) do update
set
  email = excluded.email,
  display_name = excluded.display_name,
  updated_at = now();

3. 재발 방지 체크리스트

Vercel 프로젝트 설정 server/next-app를 Root Directory로 사용하고, Output Directory는 비운다. /api/health가 먼저 동작하는지 확인한다.
클라이언트 API 주소 운영과 Preview에서는 같은 origin의 /api를 사용한다. 로컬 개발에서만 VITE_API_BASE_URL을 사용한다.
SPA 라우팅 새 클라이언트 경로를 추가하면 next.config.mjs rewrites에도 직접 접속 가능한 경로를 추가한다.
Supabase 권한 RLS 정책과 PostgreSQL GRANT를 모두 확인한다. 권한 오류가 나면 먼저 테이블 grant 상태를 확인한다.
서비스 사용자 APP_SERVICE_USER_ID는 임의 UUID가 아니라 Supabase Authentication에 실제 존재하는 User UID를 사용한다.
빌드 스크립트 Vercel 빌드가 서버 앱 기준으로 실행되더라도 클라이언트 TypeScript 빌드에 필요한 devDependencies가 설치되는지 확인한다.
